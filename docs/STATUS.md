- 1.16 Sign in with Google (D-22), built at the start of Phase 2 because the 30 Oct roadmap update added it to Phase 1.
  - **Shape.** Google proves the first factor only.
    - A callback (`POST /v1/auth/google/sessions`) never returns a session. It returns either a challenge (finished by the existing TOTP verification, or a new Google passkey challenge) or an enrolment token, when the account has no second factor yet; the first session exists only once TOTP or a passkey is enrolled.
    - Sessions record `auth_method` (`password`, `passkey`, `google`). The TOTP challenge token carries the first factor's method, so the session it completes records `google`.
    - Google never sets `step_up_at`.
    - 13 operations under `/v1/auth/google/…`.
    - Five new codes: `AUTH-4018` failed flow or token, `AUTH-4019` SSO domain, `AUTH-4020` account exists so link first, `AUTH-4021` linked to someone else, `AUTH-4022` only way in. `AUTH-4017` stays reserved by ADR 0006.
  - **Flow state** (state, nonce, PKCE verifier, intent, and the user for a link) lives in Redis for 10 minutes and is taken with GETDEL, so a state works once. Each nonce belongs to one state, so a replayed ID token fails too.
  - **Matching** is on `sub` in the new `identity.user_identities` table. An unlinked Google account whose email belongs to an existing user gets AUTH-4020, and nothing is linked.
  - **Linking** needs session + step-up, and the link callback must come from the same user who started it. This blocks an attacker's link flow being completed in a victim's session.
  - **Unlinking** is refused when the user has no password and no passkey.
  - **SSO domain check:** `sso_connections` has FORCE RLS, so the cross-tenant lookup uses a new NOLOGIN `identity_sso_domain_lookup` role (`WITH INHERIT FALSE`, used only through `WithRoleTx`), 1.8's pattern. This role is a deviation from data model §3. SSO itself is still deferred to 20.8, so a match is a refusal, not a redirect.
  - **Migration** `20261030120000_add_google_sign_in.sql` adds `user_identities` (copied from data model §3), `sessions.auth_method`, and the role. Existing session rows were backfilled to `password` (approved; dev and test data only).
  - **`auth_method`** is also in `listSessions`' `SessionSummary`: the e2e needs it, and users see how each session signed in.
  - **Dependencies:** `coreos/go-oidc/v3 v3.21.0`, `golang.org/x/oauth2 v0.37.0` (already an indirect dependency at v0.36), and `go-jose/v4 v4.1.4` as an indirect dependency.
  - **Config:** `IDENTITY_GOOGLE_CLIENT_ID`, `_CLIENT_SECRET`, `_REDIRECT_URL`, `_ISSUER`. All optional: with no client ID, Google is off and its routes return VAL-4003. Google's discovery document is fetched lazily, so identity starts even if Google is unreachable.
  - **`tools/fakes/oidc`** is a real HTTP OIDC provider: discovery, JWKS, a token endpoint that checks PKCE, and RS256 ID tokens with tamper options. The real go-oidc adapter runs unchanged against it.
  - **Refactors, behaviour unchanged:** `finishPasskeyLogin`, `storeNewPasskey` and `confirmTOTPEnrollment` were split out of existing code for reuse.
  - **Tests.**
    - App level:
      - tampered or foreign-key signature, expired token, wrong audience or issuer, foreign nonce, unknown or reused state, a link state used for sign-in, unverified email;
      - Google + TOTP and Google + passkey both give `auth_method=google` and no step-up;

- 1.5 Sessions in PostgreSQL with a Redis cache; list and revoke sessions; sign out everywhere. The PostgreSQL half already existed (1.3's `createSession`/`GetActiveSessionByID`) — this task added the Redis cache data model §3 promises ("cached in Redis for the gateway's per-request check") plus the three new use cases. **Cache is populated lazily, not write-through at sign-in** — a deliberate deviation from this task's own plan, found during implementation: write-through inside `createSession` would race against its enclosing `pgx.BeginFunc` (every call site already ends with `createSession` as the transaction's last statement, so a cache entry could in principle validate a session whose insert later rolls back). `ResolveSession` (Redis-then-Postgres, the exact "per-request check" data model §3 means, and `requireSession`'s own lookup now goes through it) populates the cache only on a Postgres hit; the cost is one guaranteed miss on the first request after sign-in, which is negligible. A genuine Redis error (not just a miss) degrades to the Postgres path rather than failing authentication. `last_seen_at` is bumped only on that Postgres path too, not on every cache hit, so the cache stays a speedup rather than a write-amplifier — the column now means "last time this session needed a database round trip." **Sign out everywhere revokes every active session, including the one making the request** (your call) — both it and single-session revoke evict the Redis key in the same call that sets `revoked_at`, so a revoked session can never still validate from a stale cache entry. Listing shows active sessions only (`revoked_at IS NULL AND expires_at > now()` — data model §3's own `sessions_active` partial index already anticipated exactly this query). `api/session.go`'s `SessionLookup` now wraps `*app.Service` and calls `ResolveSession` instead of querying Postgres directly — `requireSession`'s bearer-check and the real gateway's eventual per-request check (1.11) are the same code path now, not two. No new catalogue code (reuses 1.4's `VAL-4003`); no new dependency (`redis/go-redis/v9` was already in `go.mod` via `platform/cache`, built in 0.9 but unused until now). Added `testkit.StartRedisURL`, mirroring `StartNATSURL`'s existing pattern, since `identity.Config` now needs a real Redis connection string in tests, not an in-process client.
- 1.6 Step-up MFA for sensitive actions, as listed in system design §3. System design's step-up list ("create or reveal credentials, change callback URLs, approve payouts, add users, or edit sender IDs") is mostly for features later phases haven't built yet — the only matches that exist today are starting TOTP enrollment and starting passkey registration, both literally "create credentials," so those are the two gated. **Decided with you: step-up is proved with the account's existing TOTP code when enrolled, otherwise a one-time emailed code** — no passkey-specific step-up ceremony (adding a second passkey steps up via TOTP or email, not a fresh WebAuthn assertion); this also resolves the chicken-and-egg case for an account's very first credential enrollment, which has neither TOTP nor a passkey yet to step up with. - 1.9 HMAC request signing for high-value calls: signature over method, path, body and timestamp, valid for 5 minutes, with replay protection. **Scope question resolved with you first**: system design §3's "high-value calls (payouts, B2B, wallet transfers)" don't exist anywhere in this codebase yet — payments is Phase 3+. Decided: build only the generic, reusable verification mechanism (new `platform/hmacauth`), fully tested against the phase's own three named cases, with no new identity schema and no route wired to it — same "only gate what currently exists" instinct 1.6 used for step-up and 1.8 used for IP allowlist/spend cap enforcement. Whichever future task builds the first real high-value endpoint (likely payments) decides where the signing key's storage comes from, against an actual need rather than a speculative one. **Second thing resolved with you**: 1.7's `api_client_secrets.secret_hash` is Argon2id (one-way) and can never be used to recompute an HMAC, so `hmacauth.Middleware` takes the signing key via a caller-supplied `KeyFunc(ctx, clientID) ([]byte, error)` rather than querying any table itself — this task adds zero schema. `hmacauth.Middleware` is a plain net/http middleware, not an oapi-codegen `StrictMiddlewareFunc` like `requireSession`/`requireStepUp` (1.4/1.6) — the strict-server decodes the body into a typed struct *before* any `StrictMiddlewareFunc` runs, so by then it's too late to hash the exact bytes a client signed; this reuses `platform/idempotency.Middleware`'s own read-and-restore-the-body pattern for the same reason, not a new one. Canonical signed string is `method + "\n" + path + "\n" + timestamp + "\n" + body` (`hmacauth.CanonicalString`, exported for a future client SDK to reuse exactly); headers are `X-Signature` (hex HMAC-SHA256), `X-Signature-Timestamp` (unix seconds), `X-Signature-Nonce` — no existing header-naming convention in this repo beyond the bare `Idempotency-Key`, so these follow common signed-webhook practice. The caller (who the request is *from*) comes from context (`hmacauth.WithClientID`/`ClientID`), standing in for the gateway's JWT-auth middleware (task 1.11) that would normally set it before this check ever runs — never read from a header here. Verification order is timestamp window → signature → nonce claim: checking the signature *before* claiming the nonce means a wrong signature never burns a nonce a legitimate retry might need, and claiming only on a verified signature is what actually catches a replay of a previously-valid request. Nonce replay protection is Redis `SETNX` (`hmacauth.RedisNonceStore`, wrapping `platform/cache`), TTL equal to the signature's own validity window (5 minutes) — intentionally *not* reusing `platform/idempotency.Store`'s claim mechanism despite the structural similarity, since idempotency's whole point is replaying the *same* cached response for a legitimate retry, the opposite of what replay protection wants (reject a replayed request outright). One new catalogue code, `AUTH-4013` ("HMAC signature invalid or request expired"), bundles wrong signature, stale/future timestamp and replayed nonce alike — same "don't distinguish" anti-enumeration principle every other auth-adjacent code here already uses; a missing `ClientID` in context (this middleware wired in before JWT auth) renders `SYS-9000` instead, since that's a wiring bug, not a client error.

- 1.12 Security events log; login alerts by email. Scoped tightly to system design §3's own audit sentence — "every credential event (created, used from a new IP, rotated, revoked) is logged and shown to the tenant admin" — rather than logging every possible identity action (TOTP/passkey enrollment, password reset, session revoke, step-up aren't named there, so they're deliberately left alone; a future task can add them if the design ever actually asks). **"Used from a new IP" → sign-in.** `identity.security_events` already existed (1.1) and already recorded `sign_in_failed` (1.3's lockout window), but no *successful* sign-in was ever logged before this task, across any of the three sign-in paths (password, TOTP, passkey). A `nil` IP (caller IP unparseable) skips the check entirely rather than guessing. **New `EmailSender.SendLoginAlert` method is the one exception to this service's "email failure propagates" convention** (established by signup/password-reset/step-up, all essential to their own flow) — a login alert is a best-effort notice about a sign-in that already succeeded, so `Service.sendLoginAlert` swallows its own error rather than failing the sign-in over a transient SMTP hiccup; documented inline specifically because it's a deliberate deviation from the existing pattern, not an oversight. **"Created/rotated/revoked" → the two credential lifecycle gaps 1.7 and 1.10 each left behind**: neither `api_clients`' create/rotate/revoke nor `smpp_accounts`' create/rotate-password/suspend/reactivate ever wrote a security event — this task fills both, reusing one shared `recordSecurityEvent` helper (marshals a `map[string]any` detail to the column's `jsonb`). These write with `ip = nil`: the handlers that call them don't carry caller-IP context today, and the design sentence's "used from a new IP" is specifically a sign-in concept, not a requirement on credential-management calls — threading IP through every API-client/SMPP handler for events that don't need it would be scope creep for this task. **New `GET /v1/auth/security-events`** ("shown to the tenant admin" — this phase's placeholder is the account's own owner, same reasoning every other Phase 1 list uses) reuses the existing `ListSecurityEventsByUser` query, now bounded at `LIMIT 100` (true cursor pagination still isn't built anywhere in this API; same "only build what's needed now" call every other Phase 1 list already makes). No step-up: listing one's own audit log isn't "create or reveal a credential." **Found and fixed a real bug in a shared test helper, by testing**: `signUpVerifyAndSetPassword` (introduced in 1.6, reused by every Phase 1 API test since) hardcoded its `Idempotency-Key` values (`"signup-key"`, `"verify-key"`, ...) — harmless as long as every test called it for exactly one account, which every test until this one did. This task's own list-endpoint test needed two accounts in one test for the first time, and the second `signUpVerifyAndSetPassword` call collided on the same key with a different body (`VAL-4001`, since every pre-auth call shares one anonymous tenant). Fixed by suffixing every key with the account's own email — collision-free for the new two-account test and a no-op for every existing single-account call site.
- 1.13 v3 importer: users and profiles. **Real design gap, no v3 database or export access exists in this environment to resolve it against** (CLAUDE.md: never connect to v3 production or its database) — data model §3's "From v3" table names v3's own columns (`user.email_address`, `user.full_names`, `user.password`, `profile.msisdn`) but never an export mechanism. New `platform/crypto` primitives (explicitly deferred here back in 0.11's own notes): `IsBcryptHash` detects a stored hash's *encoding*, not a flag — bcrypt's `$2a$`/`$2b$`/`$2y$` prefix and Argon2Hash's own `$argon2id$` prefix are already disjoint, so no new column is needed to tell a freshly-imported v3 hash apart from a native one; `BcryptMD5Verify` reproduces v3's exact scheme (bcrypt of the hex-encoded MD5 of the password — MD5 only as v3's own already-baked-in pre-hash step, never used to produce anything new). `SignIn` branches on `IsBcryptHash` and, on a successful legacy verify, immediately calls the existing `SetPasswordHash` query with a fresh `Argon2Hash` of the same password, inside the same transaction as the sign-in itself — so the account is upgraded by the time the response goes out, and every sign-in after this one goes through `Argon2Verify` like any native v4 account. A wrong password against a legacy hash fails exactly like any other wrong password (same `ErrBadCredentials`, same lockout counter) and leaves the hash untouched. **Idempotency is by email, not a new `v3_id` column** — identity.users.email is already the data model's own globally `UNIQUE` sign-in identity, so `CreateV3ImportedUser`'s `ON CONFLICT (email) DO NOTHING RETURNING *` already gives free, correct idempotency (a conflict comes back as `pgx.ErrNoRows`, reported "skipped," not an error) for both a re-run of the same batch and a duplicate email within one batch; sending a fresh verification code would be pointless friction, not a safety improvement. **A record with no usable email is flagged, not imported** (task's own literal instruction) — reuses `domain.NormalizeEmail` exactly as sign-up does, so the same email rules apply on the way in as on the way out. **Phone is best-effort, never a reason to flag**: `domain.NormalizeV3MSISDN` (new, deliberately Kenya-specific — v3 is Kenya-only per requirements.md, and this is one-time import glue, not the ongoing per-country business rule CLAUDE.md's "country rules live in packs" is actually about) converts the common local forms (leading `0`, leading `254`, already `+254`) to E.164; ## Notes for next session
- **A Postgres role grant defaults to INHERIT, which silently defeats a "narrow, transaction-scoped elevated role" design (1.8, found by testing).** `GRANT identity_token_exchange TO CURRENT_USER` (no `WITH INHERIT FALSE`) made that role's extra RLS policy match on *every* query the granted connection ever ran — not just inside the one `db.Pool.WithRoleTx` transaction meant to scope it — because INHERIT makes a role's privileges ambiently active for any member, with no `SET ROLE` required at all. `SET ROLE`/`SET LOCAL ROLE` only matters for *non-inheriting* membership; with a default (inheriting) grant it's a no-op the privilege didn't need. Any future "narrow role reached only via an explicit SET ROLE" design needs `WITH INHERIT FALSE` on the grant, or the narrowing is fiction. Caught by a test asserting the *absence* of access outside the elevated-role block — the kind of negative assertion that's easy to skip when the happy path already passes.
- **No application service has any local-dev env var documented anywhere in this repo yet (1.8, found while trying to extend one).** `deploy/compose/docker-compose.yml` only runs infra containers (Postgres/Redis/NATS/RabbitMQ/ClickHouse/SeaweedFS/Mailpit/otel-lgtm) — `cmd/identity`/`cmd/vaspro-all` aren't compose services at all — and `deploy/compose/env.example` only documents those infra containers' own superuser credentials, not one single `IDENTITY_*` value (not even 1.3's `IDENTITY_TOTP_KMS_KEY`, let alone this task's new `IDENTITY_SIGNING_KEYS_KMS_KEY`). Whoever runs `cmd/identity`/`make run` locally today must already be exporting every `IDENTITY_*` env var some other way (shell profile, a local untracked `.env`, etc.) — there's no committed convenience file for it. Worth fixing with one actual task rather than each future one inventing its own partial answer.
- **`FORCE ROW LEVEL SECURITY` blocks reads too, not just writes, and fails silently (zero rows), not with an error (1.7, found by testing).** `api_clients` is the first RLS-enabled table any identity app/ code has actually touched — every earlier Phase-1 table (`users`, `sessions`, `user_totp`, ...) has none, so every earlier `app/` file used a plain `pgx.BeginFunc`/`store.New(s.pool)` without a second thought. A first draft of `GetApiClient`/`ListApiClients` did the same — plain reads outside `db.Pool.WithTenantTx` — and they compiled, ran, and returned empty results with no error, because `nullif(current_setting('app.tenant_id', true), '')::uuid` is `NULL` with no tenant transaction, and `tenant_id = NULL` is never true in SQL regardless of what the query's own `WHERE` clause already says. Fixed by wrapping every query against `api_clients`/`api_client_secrets` — reads included — in `WithTenantTx`. 1.1's own `TestAssertRowLevelSecurity_OnAPIClients` was already proof RLS itself works; it just never exercised this exact bug, since it never went through `app/apiclients.go`'s code. Any future service's first RLS-enabled table deserves the same suspicion: a `nil`-looking result from a seemingly-correct query is this bug's signature, not a crash.
- **Writing a new query file without reading the existing one first silently clobbers it (1.7, found by testing).** `internal/identity/store/queries/api_clients.sql` already existed from 1.1 (two minimal starter queries); writing a fresh file to the same path overwrote it rather than erroring, since the harness only knows a file is tracked once something in the session has actually read it. No capability was lost here — confirmed via `git diff` before moving on, and the one other caller (`store_integration_test.go`, 1.1's own RLS proof test) just needed updating to the new query names (sqlc renamed `CreateAPIClient`→`CreateApiClient` purely from how the `-- name:` comment was capitalized, not a version change) — but it could easily not have been a safe overwrite. Read first, every time, even for a path that *feels* new.
- **A brand-new operation left out of `requireSessionOperations` doesn't fail loudly — it just never gets checked (1.6, found by testing).** The three new step-up operations (`CreateStepUpTotpVerification`/`CreateStepUpEmail`/`CreateStepUpEmailConfirmation`) were wired into handlers.go and the OpenAPI spec but forgotten from `requireSessionOperations` itself. The symptom was identical to 1.3's case-mismatch bug (a 500 instead of a 401 — `createStepUpEmail` fell through to `RequestStepUpEmail(ctx, uuid.Nil)`, a lookup for a user that doesn't exist, wrapped into a generic error, SYS-9000) but the cause this time was a missing map entry, not a wrong-case one. Caught the same way: the api-layer "rejects a missing bearer" test for the new routes failed with 500 instead of 401. Any task that adds a session-bearer route needs two edits in `middleware.go`, not one — the gating map AND whichever operation map a new cross-cutting check (like `requireStepUp`) also needs — and a rejection-path test is what actually catches a forgotten entry, since nothing else will.
- **`platform/idempotency.Middleware` applied itself to every HTTP method, not just writes — a real bug, fixed (1.4, found by testing).** `.claude/rules/api.md` requires the `Idempotency-Key` header on every *write*; the middleware didn't check the method at all, so it rejected GETs too — invisible until 1.4 added identity's first-ever GET endpoint (`listPasskeys`), which then failed every call with VAL-4000 ("the Idempotency-Key header is required") despite its own OpenAPI contract never asking a reader to send one. Fixed by short-circuiting the middleware for GET/HEAD/OPTIONS before it even looks at the header, with a new unit test (`TestMiddleware_GetRequestWithNoHeader_RunsAnyway`). This is a platform-level fix, so it protects every future service's read endpoints too, not just identity's.
- **oapi-codegen's `StrictMiddlewareFunc` is called with the generated Go method name, not the OpenAPI `operationId` string (1.3, found by testing).** `requireSession`'s gating map used `"createTotpEnrollment"` (the YAML's `operationId`, lowerCamelCase) but the actual call site (`strictHandler.CreateTotpEnrollment` in `api_gen.go`) passes `"CreateTotpEnrollment"` (PascalCase, the Go method name) — a silent map-key miss, not a compile error. The middleware never rejected anything; both TOTP-enrolment routes 500'd instead of 401'ing, because the real handler ran with no session, called `GetUserByID(ctx, uuid.Nil)`, got `pgx.ErrNoRows`, and that wrapped-but-unmatched error fell through `toProblem`'s default case to a generic SYS-9000. - Added `platform/testkit.StartNATSURL(t) string` alongside the existing `StartNATS(t) *bus.Bus` — needed once 0.13's scaffold test had to hand a NATS URL to a subprocess (`cmd/demo`) rather than use an in-process client. `StartNATS` now calls it internally; existing callers are unaffected.
- `platform/outbox.Write` and `platform/inbox.MarkProcessed` use unqualified table names (`outbox_events`, `processed_events`) — they rely entirely on the connection's `search_path` already pointing at the calling service's schema. Nothing enforces this at the type level; a service that forgets `search_path=<name>` on its `DatabaseURL` gets cryptic "relation does not exist" errors, not a clear one. Worth a clearer error or a doc callout if this bites someone in Phase 1.
- `platform/idempotency.Middleware` needs `log.TenantID(ctx)` already set, which only a gateway's auth middleware can do (Phase 1) — 0.13's generated service deliberately does *not* wire `idempotency.Middleware` on its write endpoint yet, even though data model §1 says every schema gets an `idempotency_keys` table (which the generated migration does create). Each real service wires the middleware once the gateway supplies tenant context.
- `platform/testkit` deliberately has no factories for tenants/users/wallets/messages (ROADMAP §8.4 names them) — those schemas belong to `accounts`, `identity` and `messaging`, none of which exist yet in Phase 0, and `platform` holds mechanisms only, never business logic (CLAUDE.md). Each service should add its own factories once its own schema and sqlc code land; `testkit`'s `doc.go` states this explicitly so it isn't mistaken for an oversight later.
- Adding `github.com/pressly/goose/v3@v3.29.0` for 0.12 dragged several *other* transitive dependencies forward too (`golang.org/x/crypto` 0.57.0→0.58.0, `google.golang.org/grpc` 1.83.2→1.84.0, moby/docker-related packages, etc.) — verified this is goose's own `go.mod` requiring those newer versions as indirect deps (Go's MVS/graph-pruning pulls them in), not the silent, unexplained kind of drift 0.9 ran into. `go mod tidy`'s diff showed only additions paired with version bumps, nothing dropped without a newer replacement.
- `platform/crypto`'s `KMS` interface only has `LocalKMS` (dev/test) implementing it so far — no design doc fixes a shape for the real Cloud KMS/Vault implementation yet, so that's deferred to whichever later task actually needs it (likely alongside payments' `rail_credentials` or identity's secrets). Also explicitly deferred: JWT/JWKS signing (`identity.signing_keys`, EdDSA — identity's task, uses `lestrrat-go/jwx` directly), the v3 bcrypt(MD5) one-time verify path (task 1.13), and the actual HMAC request-signing flow with replay/nonce checking (task 1.9) — 0.11 only shipped the `HMACSign`/`HMACVerify` primitive those will build on.
- `golang.org/x/crypto` was already an indirect dependency (pulled in transitively); 0.11 just promoted it to direct in `go.mod` by importing `argon2` — `go mod tidy` held it at the same pinned `v0.57.0`, no other version moved.
- `vaspro packs validate` lives at `tools/vaspro/` (plain `package main`, dispatch by subcommand string — not `tools/scaffold`-style, not `cmd/`). ROADMAP's tree sketch doesn't show a path for it explicitly; `tools/` was picked because it's an operational/dev CLI like `tools/fakes` and `tools/scaffold`, not a long-running service like everything under `cmd/`. Revisit if a second subcommand family makes the dispatch outgrow a single `main.go`.
- `go mod tidy` silently downgraded `github.com/nats-io/nats.go` from `v1.54.0` to `v1.33.1` partway through 0.9 (presumably satisfying some other module's lower transitive requirement) — caught it because a diagnostic flagged a broken import after a tidy run that otherwise reported success. Re-ran `go get github.com/nats-io/nats.go@v1.54.0` explicitly and it held on subsequent tidies. If any pinned version mysteriously drops after `go mod tidy`, check `go.mod` immediately rather than trusting the command's own success output.
- `platform/bus.Consume`'s dead-lettering is entirely client-side (delivery-count check + manual publish + `Term`) — JetStream has no server-side "move to this subject after N failures" config at this API surface. Any change to retry/DLQ behavior happens in `platform/bus`, not NATS server config.
- `platform/idempotency.Middleware` has a documented, deliberate gap: concurrent duplicate requests on the same key both run the handler (no lock/poll on an in-flight claim) — fine until something actually issues concurrent duplicates.
- `processed_events`' DDL (`internal/platform/inbox`) was inferred from data model §1's prose, not copied from an explicit snippet like `outbox_events`/`idempotency_keys` got — sanity-check it once a real service migration creates it.
- **RLS pattern bug, fixed (0.6):** the bare `current_setting('app.tenant_id')::uuid` pattern data model §1 documented errors instead of failing closed on a reused pooled connection. Fixed to `nullif(current_setting('app.tenant_id', true), '')::uuid` + `WITH CHECK` + `FORCE ROW LEVEL SECURITY`, now in data model §1 and `.claude/rules/migrations.md` — use that, not the version from memory.
- `gen-check` is scoped to `git diff -- ':(glob)**/*_gen.*'`. Every future generator's output must be named `*_gen.<ext>` for this to keep working. It diffs the working tree against the index, so right after `make gen` on a dirty, uncommitted tree it will "fail" on your own not-yet-staged work — expected, not a bug; stage (or commit) first and re-run to confirm it's actually clean.
- **MinIO is not in the stack** — `deploy/compose/docker-compose.yml`'s `object-storage` service runs SeaweedFS's S3 gateway instead (same ports, 9000/9001). Postgres there is on host port **5433**, not 5432.
- `go test -tags=integration ./...` run across the whole module flaked once on `internal/platform/testkit` (1.3) under heavy concurrent container load — dozens of testcontainers starting at once across packages. Reran clean twice after. Not a real regression; if it recurs, run the failing package alone before assuming something actually broke.
