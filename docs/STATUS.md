- 1.16 Sign in with Google (D-22), built at the start of Phase 2 because the 30 Oct roadmap update added it to Phase 1.
  - **Shape.** Google proves the first factor only.
    - A callback (`POST /v1/auth/google/sessions`) never returns a session. It returns either a challenge (finished by the existing TOTP verification, or a new Google passkey challenge) or an enrolment token, when the account has no second factor yet; the first session exists only once TOTP or a passkey is enrolled.
    - Sessions record `auth_method` (`password`, `passkey`, `google`). The TOTP challenge token carries the first factor's method, so the session it completes records `google`.
    - Google never sets `step_up_at`.
    - 13 operations under `/v1/auth/google/…`.
    - Five new codes: `AUTH-4018` failed flow or token, `AUTH-4019` SSO domain, `AUTH-4020` account exists so link first, `AUTH-4021` linked to someone else, `AUTH-4022` only way in. `AUTH-4017` stays reserved by ADR 0006.
  - **Flow state** (state, nonce, PKCE verifier, intent, and the user for a link) lives in Redis for 10 minutes and is taken with GETDEL, so a state works once. Each nonce belongs to one state, so a replayed ID token fails too.
  - **Matching** is on `sub` in the new `identity.user_identities` table. An unlinked Google account whose email belongs to an existing user gets AUTH-4020, and nothing is linked.
  - **Linking** needs session + step-up, and the link callback must come from the same user who started it. This blocks an attacker's link flow being completed in a victim's session.
  - **Unlinking** is refused when the user has no password and no passkey.
  - **SSO domain check:** `sso_connections` has FORCE RLS, so the cross-tenant lookup uses a new NOLOGIN `identity_sso_domain_lookup` role (`WITH INHERIT FALSE`, used only through `WithRoleTx`), 1.8's pattern. This role is a deviation from data model §3. SSO itself is still deferred to 20.8, so a match is a refusal, not a redirect.
  - **Migration** `20261030120000_add_google_sign_in.sql` adds `user_identities` (copied from data model §3), `sessions.auth_method`, and the role. Existing session rows were backfilled to `password` (approved; dev and test data only).
  - **`auth_method`** is also in `listSessions`' `SessionSummary`: the e2e needs it, and users see how each session signed in.
  - **Dependencies:** `coreos/go-oidc/v3 v3.21.0`, `golang.org/x/oauth2 v0.37.0` (already an indirect dependency at v0.36), and `go-jose/v4 v4.1.4` as an indirect dependency.
  - **Config:** `IDENTITY_GOOGLE_CLIENT_ID`, `_CLIENT_SECRET`, `_REDIRECT_URL`, `_ISSUER`. All optional: with no client ID, Google is off and its routes return VAL-4003. Google's discovery document is fetched lazily, so identity starts even if Google is unreachable.
  - **`tools/fakes/oidc`** is a real HTTP OIDC provider: discovery, JWKS, a token endpoint that checks PKCE, and RS256 ID tokens with tamper options. The real go-oidc adapter runs unchanged against it.
  - **Refactors, behaviour unchanged:** `finishPasskeyLogin`, `storeNewPasskey` and `confirmTOTPEnrollment` were split out of existing code for reuse.
  - **Tests.**
    - App level:
      - tampered or foreign-key signature, expired token, wrong audience or issuer, foreign nonce, unknown or reused state, a link state used for sign-in, unverified email;

- 1.3 Password sign-in with Argon2id; TOTP enrolment and verification; recovery codes: first real production use of every `platform/crypto` primitive 0.11 built — `Envelope`/`LocalKMS` encrypts `user_totp.secret_ciphertext`, `Argon2Hash`/`Argon2Verify` hashes `users.password_hash`, `HMACSign`/`HMACVerify` signs the sign-in challenge token. No migration changes needed; 1.1's schema already had everything this task touches. **Password set and "forgot password" are one mechanism** — both go through `token_purpose = reset_password` (`POST /v1/auth/password-resets` + `/password-reset-confirmations`), since proving control of the email is the same bar either way. **Sign-in with TOTP is a two-step challenge, not a single call**: `POST /v1/auth/sessions` returns either a session or a short-lived challenge; `POST /v1/auth/totp-challenges/{challenge}/verification` (TOTP code or an unused recovery code) completes it. The challenge is a stateless, HMAC-signed `{user_id, expires_at}` token — no new table, deliberately, since inventing a "pending sign-ins" table wasn't something the data model called for. **Lockout is a rolling window, not a persisted flag**: every failed step writes a `sign_in_failed` row to `security_events`; 5 such rows in the last 15 minutes rejects before even checking the next attempt's password/code, so a lockout expires on its own as failures age out of the window — "unlock by staff" needs an admin console that doesn't exist until Phase 2's `accounts`, so that's deferred. A locked-out attempt, a wrong password, and an unknown email all return the identical `AUTH-4010` (reused from the catalogue, not new) — same anti-enumeration principle 1.2 already used for sign-up. New catalogue code **`AUTH-4011`** ("Two-factor code invalid or expired") covers a wrong TOTP code, a wrong/reused recovery code, and an expired/malformed challenge alike — same "don't distinguish" reasoning. **TOTP enrolment needs the caller already signed in** (system design §3 treats it as a dashboard setting, not sign-up), but no real gateway/JWT exists yet (tasks 1.8/1.11) — `internal/identity/api/middleware.go`'s `requireSession` is a narrow, identity-local stand-in: an oapi-codegen `StrictMiddlewareFunc` gated on operation ID, reading `Authorization: Bearer <session_id>` and resolving it through the new `GetActiveSessionByID` query (`api/session.go`'s `SessionLookup`). Recovery codes (8 per enrolment, `domain.GenerateRecoveryCodes`, crypto/rand, a 32-char no-lookalike alphabet) are shown exactly once at enrolment and hashed with plain SHA-256 (hex, not raw bytes — `user_totp.recovery_code_hashes` is `text[]`), not Argon2id, since they're random rather than human-chosen, same reasoning 1.2 applied to verification codes; consuming one is an atomic `array_remove`-and-return (`ConsumeRecoveryCode`), so a race between two uses of the same code can't both succeed. New dependency `github.com/pquerna/otp@v1.5.0` (6 digits, 30s period, ±1 step of drift), validated directly against RFC 6238's own published SHA-1 test vectors (`internal/identity/domain/totp_test.go`), not just "some code validated, trust me." Found and fixed one real bug while writing the API-layer tests — see Notes.
- 1.4 Passkeys (WebAuthn): registration, sign-in, and management of several passkeys. **Schema deviation from data-model.md, raised with the user first:** `identity.user_passkeys` only lists `credential_id`/`public_key`/`sign_count`/`name`/`created_at`/`last_used_at`, but `go-webauthn/webauthn` (ROADMAP §6's named library) unconditionally checks a stored "flags" byte (backup-eligible/backup-state/user-verified) against every login response — without persisting it, every login after registration would fail that check. New migration `20261022074003_widen_user_passkeys.sql` adds `flags smallint`, `attestation_type text`, `attestation_format text`, `transports text[]`, `clone_warning boolean` — explicit typed columns (the user's choice over one opaque blob column), matching the library's own documented "recommended" persistence shape. The WebAuthn "user handle" is `users.id` directly (16 bytes, no separate handle table — VASPRO is one relying party in Phase 1). Registration/login ceremony state (`webauthn.SessionData`) is a stateless, HMAC-signed opaque token, the exact `issueChallenge`/`verifyChallenge` pattern 1.3 built for the TOTP sign-in challenge (refactored into two shared helpers, `signPayload`/`verifyPayload`, so both features now share one signing primitive) — go-webauthn's own package doc explicitly endorses this as one of its two supported approaches. Sign-in is email-first, non-discoverable (`BeginLogin`/`FinishLogin` against a known user, matching system design's literal "email plus passkey" wording) — `BeginLogin` errors outright on an account with zero credentials, so `BeginPasskeyLogin` falls back to a `fakeWebAuthnUser` (random ID + one bogus credential) for an unknown email or a real account with no passkeys, keeping the response structurally identical either way (same anti-enumeration principle 1.2/1.3 already applied elsewhere). A sign-count regression (`Authenticator.CloneWarning`, set by the library itself) is treated as a sign-in failure through the existing rolling-lockout machinery, same as a wrong password. New catalogue code `AUTH-4011`'s sibling for this task is `VAL-4003` ("Resource not found") for the passkey rename/delete ownership check — "doesn't exist" and "isn't yours" aren't distinguished. New dependencies: `github.com/go-webauthn/webauthn` (production) and `github.com/descope/virtualwebauthn` (test-only — a software WebAuthn authenticator simulator; its `Credential.Counter` is a plain mutable field, which is what makes ROADMAP's named test, "a sign counter that goes backwards is rejected," actually exercisable without a real browser). Found and fixed one real bug — see Notes.
- 1.5 Sessions in PostgreSQL with a Redis cache; list and revoke sessions; sign out everywhere. The PostgreSQL half already existed (1.3's `createSession`/`GetActiveSessionByID`) — this task added the Redis cache data model §3 promises ("cached in Redis for the gateway's per-request check") plus the three new use cases. **Cache is populated lazily, not write-through at sign-in** — a deliberate deviation from this task's own plan, found during implementation: write-through inside `createSession` would race against its enclosing `pgx.BeginFunc` (every call site already ends with `createSession` as the transaction's last statement, so a cache entry could in principle validate a session whose insert later rolls back). `ResolveSession` (Redis-then-Postgres, the exact "per-request check" data model §3 means, and `requireSession`'s own lookup now goes through it) populates the cache only on a Postgres hit; the cost is one guaranteed miss on the first request after sign-in, which is negligible. A genuine Redis error (not just a miss) degrades to the Postgres path rather than failing authentication. `last_seen_at` is bumped only on that Postgres path too, not on every cache hit, so the cache stays a speedup rather than a write-amplifier — the column now means "last time this session needed a database round trip." **Sign out everywhere revokes every active session, including the one making the request** (your call) — both it and single-session revoke evict the Redis key in the same call that sets `revoked_at`, so a revoked session can never still validate from a stale cache entry. Listing shows active sessions only (`revoked_at IS NULL AND expires_at > now()` — data model §3's own `sessions_active` partial index already anticipated exactly this query). `api/session.go`'s `SessionLookup` now wraps `*app.Service` and calls `ResolveSession` instead of querying Postgres directly — `requireSession`'s bearer-check and the real gateway's eventual per-request check (1.11) are the same code path now, not two. No new catalogue code (reuses 1.4's `VAL-4003`); no new dependency (`redis/go-redis/v9` was already in `go.mod` via `platform/cache`, built in 0.9 but unused until now). Added `testkit.StartRedisURL`, mirroring `StartNATSURL`'s existing pattern, since `identity.Config` now needs a real Redis connection string in tests, not an in-process client.
- 1.6 Step-up MFA for sensitive actions, as listed in system design §3. System design's step-up list ("create or reveal credentials, change callback URLs, approve payouts, add users, or edit sender IDs") is mostly for features later phases haven't built yet — the only matches that exist today are starting TOTP enrollment and starting passkey registration, both literally "create credentials," so those are the two gated. **Decided with you: step-up is proved with the account's existing TOTP code when enrolled, otherwise a one-time emailed code** — no passkey-specific step-up ceremony (adding a second passkey steps up via TOTP or email, not a fresh WebAuthn assertion); this also resolves the chicken-and-egg case for an account's very first credential enrollment, which has neither TOTP nor a passkey yet to step up with. Built the mechanism on `identity.sessions.step_up_at`, in the schema since 1.1 and unused until now: `app.Service.StepUpFresh` checks it's set and within a 5-minute window (matching the existing `challengeTTL` precedent), always reading Postgres directly rather than the 1.5 Redis session cache — that cache's long TTL makes it wrong for any check that has to mean "proved *just now*." `requireStepUp` is a second `StrictMiddlewareFunc`, composed after `requireSession` in `routes.go`'s slice (same iterative-wrap mechanic 1.2 documented: last entry runs first) so it can read the session ID `requireSession` resolves. Gates only the two begin operations, not their confirmation steps — gating those too could fail an already-in-progress enrollment ceremony if the window lapses mid-flow, a self-inflicted UX bug rather than a security property — and not delete/revoke actions, which aren't on system design's list. TOTP step-up reuses the sign-in rolling lockout; email step-up reuses the per-token attempt cap `ConfirmPasswordReset` already has — two different pre-existing mechanisms, each reused for the flow shape it already matches. New catalogue code **`AUTH-4012`** ("Step-up verification required") is `requireStepUp`'s own rejection, distinct from `AUTH-4010` so a client can tell "ask the user to step up" apart from "ask the user to sign in"; wrong codes for either step-up method reuse existing codes (`AUTH-4011`, `VAL-4002`). `EmailSender` grew `SendStepUpCode` — this is an authenticated action, so unlike the anonymous email flows there's no enumeration concern to preserve. Found and fixed one real bug while writing the API-layer tests — see Notes.
- 1.7 API clients: create, rotate (two active secrets), revoke; scopes, IP allowlist, expiry, spend cap; the secret is shown once and stored hashed. CRUD management only — exchanging a client's secret for a token is task 1.8, not this one; scopes/IP allowlist/spend cap are stored as configuration, enforced by nothing yet (no gateway, no billing/ledger). **Two schema/doc gaps found, resolved with you first:** (1) both system design §3 and this task's own wording call for a "spend cap" that data-model.md's literal `CREATE TABLE identity.api_clients` doesn't have — new migration `20261022215655_add_api_client_spend_cap.sql` adds `spend_cap_minor bigint`/`spend_cap_currency text`, both nullable, matching Part 1's "money as bigint minor units + currency" rule. - 1.8 OAuth2 client-credentials token endpoint; JWT signing keys with rotation; JWKS endpoint. **Design question resolved with you first**: the token endpoint has no session/tenant context and `api_clients` has `FORCE ROW LEVEL SECURITY` — chose a narrow, SELECT-only RLS policy for one new Postgres role (`identity_token_exchange`, migration `20261022223744_add_oauth_token_exchange.sql`) over `BYPASSRLS` on the whole service, so RLS stays a real backstop everywhere else. The role is `NOLOGIN` — never a connection credential to provision/rotate — reached only via a new `platform/db.Pool.WithRoleTx(ctx, role, fn)` (`SET LOCAL ROLE`, sibling to `WithTenantTx`), scoped to the one lookup transaction. **Second design question resolved with you**: `POST /v1/oauth/token` is exempted entirely from api.md's "every write needs Idempotency-Key" rule (`api/routes.go`'s `skipIdempotencyFor`) — off-the-shelf OAuth2 client libraries never send that header, and minting a token twice has no side effect worth deduplicating. Request/response follow RFC 6749 exactly: `application/x-www-form-urlencoded` body (oapi-codegen's `Formdata` binding, confirmed to work with a named/`$ref`'d schema via its `json`-tag fallback, not just inline schemas), and failures render RFC 6749 §5.2's `{"error": "...", "error_description": "..."}` shape — the one deliberate exception to problem+json in this whole API — reusing the existing `ErrBadCredentials`/`ErrValidation` sentinels, just rendered differently by this one handler. Applied the same fix to `platform/db`'s own `WithRoleTx` test fixture. **Plan's assumption about `deploy/compose/docker-compose.yml` was wrong**: investigated and found identity isn't containerized there at all yet (compose only runs infra — Postgres/Redis/NATS/etc. — `cmd/identity`/`cmd/vaspro-all` aren't compose services), and `deploy/compose/env.example` only documents infra-container credentials, not one single `IDENTITY_*` application env var (not `IDENTITY_TOTP_KMS_KEY` from 1.3, not this task's new one) — so there was no existing pattern to extend; skipped that plan step rather than inventing one inconsistently for just this task's own variable.
- 1.9 HMAC request signing for high-value calls: signature over method, path, body and timestamp, valid for 5 minutes, with replay protection. **Scope question resolved with you first**: system design §3's "high-value calls (payouts, B2B, wallet transfers)" don't exist anywhere in this codebase yet — payments is Phase 3+. Decided: build only the generic, reusable verification mechanism (new `platform/hmacauth`), fully tested against the phase's own three named cases, with no new identity schema and no route wired to it — same "only gate what currently exists" instinct 1.6 used for step-up and 1.8 used for IP allowlist/spend cap enforcement. Whichever future task builds the first real high-value endpoint (likely payments) decides where the signing key's storage comes from, against an actual need rather than a speculative one. **Second thing resolved with you**: 1.7's `api_client_secrets.secret_hash` is Argon2id (one-way) and can never be used to recompute an HMAC, so `hmacauth.Middleware` takes the signing key via a caller-supplied `KeyFunc(ctx, clientID) ([]byte, error)` rather than querying any table itself — this task adds zero schema. `hmacauth.Middleware` is a plain net/http middleware, not an oapi-codegen `StrictMiddlewareFunc` like `requireSession`/`requireStepUp` (1.4/1.6) — the strict-server decodes the body into a typed struct *before* any `StrictMiddlewareFunc` runs, so by then it's too late to hash the exact bytes a client signed; this reuses `platform/idempotency.Middleware`'s own read-and-restore-the-body pattern for the same reason, not a new one. Canonical signed string is `method + "\n" + path + "\n" + timestamp + "\n" + body` (`hmacauth.CanonicalString`, exported for a future client SDK to reuse exactly); headers are `X-Signature` (hex HMAC-SHA256), `X-Signature-Timestamp` (unix seconds), `X-Signature-Nonce` — no existing header-naming convention in this repo beyond the bare `Idempotency-Key`, so these follow common signed-webhook practice. The caller (who the request is *from*) comes from context (`hmacauth.WithClientID`/`ClientID`), standing in for the gateway's JWT-auth middleware (task 1.11) that would normally set it before this check ever runs — never read from a header here. Verification order is timestamp window → signature → nonce claim: checking the signature *before* claiming the nonce means a wrong signature never burns a nonce a legitimate retry might need, and claiming only on a verified signature is what actually catches a replay of a previously-valid request. Nonce replay protection is Redis `SETNX` (`hmacauth.RedisNonceStore`, wrapping `platform/cache`), TTL equal to the signature's own validity window (5 minutes) — intentionally *not* reusing `platform/idempotency.Store`'s claim mechanism despite the structural similarity, since idempotency's whole point is replaying the *same* cached response for a legitimate retry, the opposite of what replay protection wants (reject a replayed request outright). One new catalogue code, `AUTH-4013` ("HMAC signature invalid or request expired"), bundles wrong signature, stale/future timestamp and replayed nonce alike — same "don't distinguish" anti-enumeration principle every other auth-adjacent code here already uses; a missing `ClientID` in context (this middleware wired in before JWT auth) renders `SYS-9000` instead, since that's a wiring bug, not a client error.
- 1.10 SMPP accounts for the existing SMPP front end: CRUD management only (create, list, get, suspend/reactivate, rotate password) — same scope split 1.9 used, since there's still no real "existing SMPP front end" caller in this codebase to verify a bind against (requirements.md: "Client SMPP binds stay on the existing SMPP front end, which posts submits to v4 like v3's `/smpp/api/create`" — that integration, and the actual password+IP-allowlist check against a live bind, is a later task's job once a real caller exists, same "only build what has a consumer" reasoning 1.9 applied to HMAC signing). Status is a toggle, not a revoke: the schema's CHECK constraint only allows `active`/`suspended` (no `revoked_at` column exists on this table, unlike `api_clients`), so `SuspendSMPPAccount`/`ReactivateSMPPAccount` are the only state-changing operations beyond password rotation — modeled over HTTP as one `PATCH /v1/auth/smpp-accounts/{id}` with a `status` body field, the same verb 1.4's `updatePasskey` (rename) already established for this API, rather than inventing per-state sub-resource endpoints. **Password rotation overwrites `password_hash` in place** — unlike API client secrets (1.7), this table has one password column, not a two-row rotation-overlap mechanism, so there's no overlap window to manage. **Listing orders by `id DESC`, not `created_at`**: this table has no `created_at`/`updated_at` columns at all (copied exactly from data model §3, same as every other Phase 1 table) — `id` is a UUIDv7 (`platform/ids`), which already sorts lexicographically in creation order, so ordering by it gives the same "newest first" result `api_clients.sql`'s explicit `created_at DESC` gets, with no new column needed. Create/rotate both require step-up (1.6) — same "create or reveal a credential" trigger as API clients; suspend/reactivate don't, same reasoning 1.7 used for revoke. `system_id` is globally `UNIQUE` (data model §3, across every tenant, not just one) — a duplicate claim surfaces as `VAL-4000` through a Postgres `23505` check (`app.isUniqueViolation`), the same code 1.7 reuses for "too many active secrets," rather than a new catalogue entry. **Found and fixed a real bug via `golangci-lint`'s gosec step, not a test**: the API handler's first draft cast the OpenAPI request's plain `int` `max_binds`/`max_tps` straight to the column's `int16`/`int32` widths with no range check — gosec's G115 rule flagged the silent-overflow risk (a value like 100000 would wrap to a small or negative `int16` instead of erroring), fixed by bounds-checking both fields against `math.MaxInt16`/`math.MaxInt32` before narrowing, returning `VAL-4000` on an out-of-range value instead of truncating it.

- 1.12 Security events log; login alerts by email. ## Notes for next session
- **A Postgres role grant defaults to INHERIT, which silently defeats a "narrow, transaction-scoped elevated role" design (1.8, found by testing).** `GRANT identity_token_exchange TO CURRENT_USER` (no `WITH INHERIT FALSE`) made that role's extra RLS policy match on *every* query the granted connection ever ran — not just inside the one `db.Pool.WithRoleTx` transaction meant to scope it — because INHERIT makes a role's privileges ambiently active for any member, with no `SET ROLE` required at all. `SET ROLE`/`SET LOCAL ROLE` only matters for *non-inheriting* membership; with a default (inheriting) grant it's a no-op the privilege didn't need. Any future "narrow role reached only via an explicit SET ROLE" design needs `WITH INHERIT FALSE` on the grant, or the narrowing is fiction. Caught by a test asserting the *absence* of access outside the elevated-role block — the kind of negative assertion that's easy to skip when the happy path already passes.
- **No application service has any local-dev env var documented anywhere in this repo yet (1.8, found while trying to extend one).** `deploy/compose/docker-compose.yml` only runs infra containers (Postgres/Redis/NATS/RabbitMQ/ClickHouse/SeaweedFS/Mailpit/otel-lgtm) — `cmd/identity`/`cmd/vaspro-all` aren't compose services at all — and `deploy/compose/env.example` only documents those infra containers' own superuser credentials, not one single `IDENTITY_*` value (not even 1.3's `IDENTITY_TOTP_KMS_KEY`, let alone this task's new `IDENTITY_SIGNING_KEYS_KMS_KEY`). Whoever runs `cmd/identity`/`make run` locally today must already be exporting every `IDENTITY_*` env var some other way (shell profile, a local untracked `.env`, etc.) — there's no committed convenience file for it. Worth fixing with one actual task rather than each future one inventing its own partial answer.
- **`FORCE ROW LEVEL SECURITY` blocks reads too, not just writes, and fails silently (zero rows), not with an error (1.7, found by testing).** `api_clients` is the first RLS-enabled table any identity app/ code has actually touched — every earlier Phase-1 table (`users`, `sessions`, `user_totp`, ...) has none, so every earlier `app/` file used a plain `pgx.BeginFunc`/`store.New(s.pool)` without a second thought. A first draft of `GetApiClient`/`ListApiClients` did the same — plain reads outside `db.Pool.WithTenantTx` — and they compiled, ran, and returned empty results with no error, because `nullif(current_setting('app.tenant_id', true), '')::uuid` is `NULL` with no tenant transaction, and `tenant_id = NULL` is never true in SQL regardless of what the query's own `WHERE` clause already says. Fixed by wrapping every query against `api_clients`/`api_client_secrets` — reads included — in `WithTenantTx`. 1.1's own `TestAssertRowLevelSecurity_OnAPIClients` was already proof RLS itself works; it just never exercised this exact bug, since it never went through `app/apiclients.go`'s code. Any future service's first RLS-enabled table deserves the same suspicion: a `nil`-looking result from a seemingly-correct query is this bug's signature, not a crash.
- **Writing a new query file without reading the existing one first silently clobbers it (1.7, found by testing).** `internal/identity/store/queries/api_clients.sql` already existed from 1.1 (two minimal starter queries); writing a fresh file to the same path overwrote it rather than erroring, since the harness only knows a file is tracked once something in the session has actually read it. No capability was lost here — confirmed via `git diff` before moving on, and the one other caller (`store_integration_test.go`, 1.1's own RLS proof test) just needed updating to the new query names (sqlc renamed `CreateAPIClient`→`CreateApiClient` purely from how the `-- name:` comment was capitalized, not a version change) — but it could easily not have been a safe overwrite. Read first, every time, even for a path that *feels* new.
- **A brand-new operation left out of `requireSessionOperations` doesn't fail loudly — it just never gets checked (1.6, found by testing).** The three new step-up operations (`CreateStepUpTotpVerification`/`CreateStepUpEmail`/`CreateStepUpEmailConfirmation`) were wired into handlers.go and the OpenAPI spec but forgotten from `requireSessionOperations` itself. The symptom was identical to 1.3's case-mismatch bug (a 500 instead of a 401 — `createStepUpEmail` fell through to `RequestStepUpEmail(ctx, uuid.Nil)`, a lookup for a user that doesn't exist, wrapped into a generic error, SYS-9000) but the cause this time was a missing map entry, not a wrong-case one. Caught the same way: the api-layer "rejects a missing bearer" test for the new routes failed with 500 instead of 401. Any task that adds a session-bearer route needs two edits in `middleware.go`, not one — the gating map AND whichever operation map a new cross-cutting check (like `requireStepUp`) also needs — and a rejection-path test is what actually catches a forgotten entry, since nothing else will.
- **`platform/idempotency.Middleware` applied itself to every HTTP method, not just writes — a real bug, fixed (1.4, found by testing).** `.claude/rules/api.md` requires the `Idempotency-Key` header on every *write*; the middleware didn't check the method at all, so it rejected GETs too — invisible until 1.4 added identity's first-ever GET endpoint (`listPasskeys`), which then failed every call with VAL-4000 ("the Idempotency-Key header is required") despite its own OpenAPI contract never asking a reader to send one. Fixed by short-circuiting the middleware for GET/HEAD/OPTIONS before it even looks at the header, with a new unit test (`TestMiddleware_GetRequestWithNoHeader_RunsAnyway`). This is a platform-level fix, so it protects every future service's read endpoints too, not just identity's.
- **oapi-codegen's `StrictMiddlewareFunc` is called with the generated Go method name, not the OpenAPI `operationId` string (1.3, found by testing).** `requireSession`'s gating map used `"createTotpEnrollment"` (the YAML's `operationId`, lowerCamelCase) but the actual call site (`strictHandler.CreateTotpEnrollment` in `api_gen.go`) passes `"CreateTotpEnrollment"` (PascalCase, the Go method name) — a silent map-key miss, not a compile error. - **`pgx.BeginFunc` rolls back on ANY non-nil return — including a deliberate business-logic sentinel, not just a real DB error (1.2, found by testing).** `VerifyEmail`'s "wrong code" path called `IncrementVerificationTokenAttempts` then returned `ErrInvalidOrExpiredCode` directly from the closure — the increment got silently rolled back every time along with the "error," so attempts never actually accumulated and the 5-attempts lockout never engaged. Fixed by deciding the business outcome (`invalid bool`) inside the transaction but only returning the sentinel error *after* `pgx.BeginFunc` returns (committing first).
