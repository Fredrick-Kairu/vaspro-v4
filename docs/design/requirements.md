## SMS engine contract (read from v3)
- Queue hand-offs (RabbitMQ direct exchange `<QUEUE>_EXCHANGE`, persistent JSON): VASPRO_QUICK_1..7 (campaign/scheduled; _6 Ghana, _7 one network), VASPRO_OUTBOX_API, VASPRO_NESTED, VASPRO_OUTBOXTEST_1..4 (bulk to uploaded numbers), VASPRO_BULK_COMPOSE (contact-group campaigns; receiver reads v3 contact tables — v4 will expand recipients itself instead), TZ_SMS / TZ_SMS_VERIFICATION on the TZ RabbitMQ server. Message fields: outbox_id (correlator), campaign_id, recipients, short_code, message, message_pages, network, gateway, alert_type, dlr_url.
- Direct gateway calls v3 makes: Kannel sendsms (smsc, account=correlator, dlr-url), MNO apps gateway (smsc, correlator, alert_type, dlr_url), Safaricom bulk API (packageId, oa, uniqueId=correlator, actionResponseURL).
- Returns: Kannel-style DLR callbacks (/v3/callback/create, /v3/SMS/Report/kannel/dlr; blast NACKs resubmitted up to 5 times); Safaricom bulk DLRs go to a separate DLR service, not v3; v3 publishes "submitted" (2000) records to VASPRO_DLR / VASPRO_SAF_DLR.
- v4 rules: same contract so engine/gateways change nothing; route entries in the country pack (hand-off, SMSC, Safaricom package and sender mapping, priority); correlator = v4 message ID; DLR intake maps raw values to DLR- reasons; retries are v4's decision (next pack route, pack limit); monitoring watches hand-off errors, engine queue depth, DLR latency per route; RabbitMQ/gateway credentials to secrets store and rotated. Client SMPP binds stay on the existing SMPP front end, which posts submits to v4 like v3's /smpp/api/create.
- Open with engine owners: correlator format/length per gateway (v3 numeric vs v4 UUIDv7); single sends via direct gateway calls or all via engine queues; how v4 receives Safaricom bulk DLRs; engine queue consumers carrying contact-group campaigns without BULK_COMPOSE.

Still open: KYC vendor, shared USSD parent codes, hosting/residency, v3 migration, pricing model; plus design-doc open points; data-model Part 1 open points (VAT inclusive vs exclusive per country, eTIMS invoicing granularity for usage, settlement window length, holds in Postgres vs Redis, meaning of v3 subscription_balance, old v3 API token compatibility window, token expiry/refunds); Part 2 open points (who sends v3 payouts — bulk_payment_transaction processed flag consumed outside v3; VAT on payout fees recorded as 1.6% in v3; bank payouts route; billing day/proration; recurring top-ups as non-tax payment requests; v3 history import depth; client shortcode balance polling frequency).

## Data model Part 1 (key choices)
- PostgreSQL 16, one schema per service, row-level security on tenant_id, UUIDv7 keys, money as bigint minor units + currency (KES/TZS exponent 2, UGX 0), timestamptz UTC, transactional outbox + idempotency_keys per schema, processed_events inbox where a schema consumes events.
- identity: users (email citext unique, phone optional), passkeys, TOTP, verification_tokens, sessions, security_events (partitioned), api_clients + secrets (two active for rotation), smpp_accounts, sso_connections, signing_keys. v3 passwords are bcrypt(md5(pw)) → verify once, re-hash Argon2id.
- accounts: tenants (type direct/reseller/sub_account, parent_tenant_id, tier), roles, memberships, services catalogue, service_country_rules, tenant_services, tier_caps, business_profiles, beneficial_owners, documents (object storage refs), kyc_checks, tier_changes.
- ledger: double-entry transactions + entries (immutable, balanced per currency), balances projection (balance_minor, held_minor), account types incl. main_wallet, service_wallet, bonus, receivable, revenue_share_payable, commission_payable, provider_clearing, suspense, reversal_clearing, revenue, tax_payable (no collection wallet, no payout float). token_products (minor_per_token config), token_lots FIFO + lot_consumptions, rate_cards (tokens_per_event, prices_include_tax, client overrides), tax_rates, holds (not journal entries), usage_batches (one usage posting per wallet per settlement window; per-message detail in ClickHouse; payout fees settle this way too; airtime/data/bills post per transaction), auto_buy_rules, reversals (maker-checker CHECK).

## Data model Part 2 (key choices)
- billing (14 tables + inbox): billing_profiles (billing_day default 1, prepaid/postpaid, auto_pay sources), plans, subscriptions (plan or recurring_topup), billable_assets register (ussd_code, shared channel, extension range, shortcode, sender_id; source_type/source_id unique), usage_accruals (from usage.posted), number_series (gapless per country/doc type), invoices (kinds recurring/usage/one_off/topup_request; source_key unique per tenant prevents double billing), invoice_lines (partial unique index per item + service_period), invoice_payments, credit_notes (maker-checker), pay_links (token hash), dunning_steps, etims_submissions, billing_runs.
- Ledger touch: recurring/one-off invoices post receivable vs revenue + VAT at issue; usage invoice posts nothing (issued as paid; tax doc for tokens used); topup_request has no VAT and credits main wallet when paid.
- payments (15 tables): rails, rail_accounts (client's or VASPRO's; uses collections/payouts/vaspro_topups), rail_credentials (KMS envelope, fingerprint, one active per kind; access tokens only in Redis), payment_intents, collection_notices (client_owned never touch ledger; VASPRO paybill matched or suspense), payment_links, payout_batches (maker-checker), batch_row_errors, payouts (fee_hold_id, value_hold_id, idempotency, pending_query before retry), payout_attempts, beneficiaries, statement_imports, statement_lines, recon_exceptions, provider_floats.
- Part 3 note: messaging schema has no route-engine tables (no SMPP binds, no failover state); country-pack routes, hand-off log and DLR mapping stay in v4.
