# Open questions

Questions found during the build that the design doesn't answer. Each one gets an ID, the date, who raised it, the task it blocks, and the answer once known (then turn it into an ADR if it changes the design).

| ID | Date | Question | Blocks | Answer |
|---|---|---|---|---|
| OQ-01 | 2026-10-21 | `identity.api_client_secrets` (data model §3) has no `tenant_id` column, unlike every other client-owned table in the schema — it's reached only through `api_client_id` → `identity.api_clients.tenant_id`, which does have RLS. Is the missing `tenant_id` intentional (join-scoped access is enough, since nothing should ever query `api_client_secrets` directly without going through its parent), or a gap that should get its own `tenant_id` + RLS policy? | Task 1.7 (API clients: create, rotate, revoke) | Intentional — no new column. Every `app/apiclients.go` query against `api_client_secrets` joins through `api_client_id` to `api_clients` (and runs inside `db.Pool.WithTenantTx`), so `api_clients`' own RLS already scopes which secrets are reachable; nothing in this codebase queries `api_client_secrets` standalone by its own `id`. (1.7, 2026-10-23) |
| OQ-02 | 2026-10-23 | No doc fixes the file/column format a v3 importer actually reads — data model §3's "From v3" table names v3's columns (`user.email_address`, `user.full_names`, `user.password`, `profile.msisdn`) but not an export mechanism, and there's no real v3 database or anonymised copy available in this environment to confirm one against (CLAUDE.md: never connect to v3 production or its database). What should `tools/migrate-v3` actually read? | Task 1.13 (v3 importer: users and profiles) | Two CSV files, `users.csv` (`id,email_address,full_names,password`) and `profiles.csv` (`user_id,msisdn,network`; `network` read and discarded), column names copied verbatim from data model §3. A placeholder, not a confirmed export format — revisit the moment real v3 export access exists; the parsing is isolated to `tools/migrate-v3/csv.go` so a different real format is a small, contained change. (1.13, 2026-10-23) |
| OQ-03 | 2026-10-23 | OIDC single sign-on (task 1.15, for v3 clients with `clients.allow_okta_login`): data model §3 gives `identity.sso_connections` (`protocol`, globally unique `domain`, `config` jsonb "metadata URL, client ID; secrets in KMS") but nothing says (1) how a tenant proves it owns a `domain` before "users at this domain sign in by SSO" applies — without verification (e.g. a DNS TXT record), whoever registers a domain first, including a public one like `gmail.com`, takes over sign-in for everyone at it; and who may create a connection (tenant admin or staff); (2) which tenant a connection binds to, when real multi-user tenants don't exist until task 2.2 (1.7's "creating user's ID" placeholder doesn't fit a connection shared by many users); (3) whether a first SSO sign-in creates a user (JIT), links to an existing password/passkey user with the same email, or is refused; whether password/passkey sign-in stays allowed for an SSO domain; and whether the IdP's MFA satisfies step-up (1.6); (4) how the IdP client secret is stored — `platform/crypto.Envelope` like TOTP secrets, inside `config` or a separate column. Also unknown: which v3 clients actually have `allow_okta_login` set. | Task 1.15 (deferred to 20.8) | Open. 1.15 deferred to Phase 20 task 20.8 by the user (2026-10-23) rather than guess any of these; answer them before 20.8 starts. |
| OQ-04 | 2026-11-02 | Reseller and sub-account tenants (task 2.2b): the design gives the schema (`tenants.type`, `parent_tenant_id`) and the requirements say the Financial tier unlocks "reseller accounts", but nothing says (1) how an account becomes a reseller; (2) who can get into a sub-account; (3) what tier a sub-account starts on; (4) which country a sub-account can be in. | Task 2.2b | Answered by the user (2026-11-02): (1) a staff action, only for an active direct account on the Financial tier (an app use case in 2.2b; the staff route comes with 2.9); (2) the reseller's active members reach its sub-accounts through the parent link, with no copied memberships; the client's own users join through 2.3's invitations; (3) sandbox, then its own KYC; (4) the reseller's country, currency, time zone and region. Following from these: only two levels (a sub-account never becomes a reseller), and a reseller that drops below Financial or is suspended or archived keeps its sub-accounts but can't add new ones. |
| OQ-05 | 2026-11-02 | Memberships, roles and invitations (task 2.3): the data model gives `roles` (built-in when `tenant_id` is NULL; "Admin, Developer, Finance, Viewer ...", permissions like `{sms:send, payouts:approve}`) and `memberships.status` (invited/active/removed, `user_id NOT NULL`), but nothing lists the permissions or the roles' contents, says whether tenants get custom roles, or says how someone is invited by email when accounts doesn't know emails and `memberships` needs a user. | Task 2.3 | Answered by the user (2026-11-02): four built-in roles over a small catalogue (`account:read/manage`, `members:read/manage`, `credentials:read/manage`, `billing:read/manage` reserved); Admin `*`, Developer credentials + read, Finance billing + read, Viewer read-only. No custom roles yet. Invitations: accounts asks identity over gRPC to find or create the user by email (identity creates an unverified user as sign-up does and sends the invite), the same answer whether or not the email existed; the invitee accepts after signing in. Split into 2.3a (roles, permissions, member management) and 2.3b (invitations). |
| OQ-06 | 2026-11-02 | Service catalogue (task 2.4): the data model gives `services`, `service_country_rules` ("country pack overrides") and `tenant_services` (selected/enabled/suspended); system design §2 says each service declares a minimum tier per country and a locked service shows the tier it needs. Nothing lists the services, says whether the pack or the table holds the country rules, what a demotion does to an enabled service, or whether a service can be removed. | Task 2.4 | Answered by the user (2026-11-02): the requirements' tier table (sms, surveys, ussd at starter; whatsapp, rewards at business; payouts, collections at financial; sender IDs, shortcodes and dedicated USSD codes are Phase 12 applications); the pack holds each country's rules and accounts syncs them into `service_country_rules` at startup; a demotion returns a service to selected (locked, `service.locked`) and the tier regained re-enables it; an account may remove a selected service (`service.deselected`). |
